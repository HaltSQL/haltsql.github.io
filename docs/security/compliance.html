Compliance mapping

This page maps HaltSQL features to controls in common security and privacy frameworks, and lists the evidence each feature can produce. It is for compliance, GRC and audit teams who need to explain where HaltSQL fits in an organization's control set.

Note: HaltSQL is open-source, self-hosted software. It is not certified or attested under SOC 2, ISO/IEC 27001, HIPAA or any other framework, and this page does not claim that it is. It maps HaltSQL features to controls that you operate. Whether a control is met depends on how you configure, run and monitor HaltSQL together with your other controls, and that responsibility stays with you and your auditor.

Where HaltSQL fits​

HaltSQL is a preventive and detective technical control for one specific access path: SQL that an LLM agent generates for PostgreSQL. It:

  • restricts access: a query can read only the relations, columns and functions the policy lists, and, for tenant-scoped tables, only the caller's tenant (tenancy.md);
  • binds callers to policies: every authenticated identity is pinned to one policy (authentication.md);
  • records decisions: one hash-chained audit record per verdict (audit-sinks.md);
  • controls policy change: policies can be tested in CI, signed, and verified by every server before use (policy-bundles.md).

It does not cover identity lifecycle, the database's own access controls, encryption at rest, backups, the data returned by allowed queries, or the prompt. Pair it with the database controls in defense-in-depth.md.

GDPR​

HaltSQL processes whatever personal data appears in SQL text and context values, in your environment. It sends nothing to the HaltSQL project.

Principle or articleHaltSQL featureEvidence
Art. 5(1)(c) Data minimisationColumn allowlists let an agent read only the columns its task needs; require_limit bounds rows; PII-flagging helps find sensitive columns (schema-and-pii.md)E3
Art. 5(1)(f) Integrity and confidentialityTenant isolation proof; TLS; hash-chained audit recordsE1, E5
Art. 25 Data protection by design and by defaultDeny by default; raw SQL not logged by default; context values not written to audit records; OPA receives no SQL and no context valuesE5
Art. 32 Security of processingAccess restriction, encryption in transit, audit, fail-closed behaviourE1, E2, E5
Art. 5(2) AccountabilityAudit records tie every decision to a caller, subject and policy versionE2, E6

Things to consider in your own records of processing:

  • Audit records contain the caller's identity (caller, and subject for OIDC and mTLS callers), which may be personal data.
  • sql_sha256 and fingerprint are not anonymisation. With audit.log_raw_sql: true the SQL text, including literals, is stored.
  • HaltSQL has no built-in retention or deletion of audit records. Retention is set where records are stored (bucket lifecycle, Object Lock period, index lifecycle, topic retention). WORM retention conflicts with erasure requests, so choose it with your DPO.

Gaps an auditor may raise​

  • HaltSQL 0.0.1 has not had an external security audit or penetration test (threat-model.md).
  • Audit records do not include the context values (for example the tenant id) of a request, or the caller's network address. Join with your application logs if you need them.
  • The audit chain is a hash chain, not a signature. It needs WORM storage or an independently kept head hash to detect whole-log rewrites.
  • HaltSQL does not encrypt anything at rest.
  • There is no switch that forbids unsigned policy files; enforce "signed bundles only" in change control (see hardening.md).
  • The sidecar and the library trust the calling code to enforce the verdict. Only the proxy enforces it itself.
