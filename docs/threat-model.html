Threat model

This page states what HaltSQL protects, who it protects against, what it assumes, and what it does not do. If you find a way to break one of the guarantees below, please report it privately (see SECURITY.md).

System​

HaltSQL receives three inputs: the SQL string, the policy, and the context. It returns a verdict. It does not run SQL, rewrite SQL, or connect to the database.

Assets​

  1. Other tenants' rows. The primary asset in multi-tenant applications.
  2. Sensitive columns (PII, credentials, salaries) that the policy omits.
  3. Database integrity: schema, data, sequences, settings, locks.
  4. Database availability: CPU, memory, I/O, connections.
  5. Server-side capabilities: files, network access, other databases, and administrative functions reachable from SQL.

Adversary​

The adversary controls the full text of the SQL, either directly (a malicious user of the agent) or indirectly (prompt injection through documents, web pages, tickets, emails, or tool output the model reads). Assume they know HaltSQL's source code and the policy.

The adversary does not control:

  • the context (tenant ID, user ID, role), which your application takes from its own authenticated session;
  • the policy and config files;
  • the code that calls HaltSQL and runs the query (it must run the exact verified string and bind exactly bind_params);
  • the database role and its privileges.

If any of these assumptions fail, HaltSQL's guarantees do not hold. In particular, never take the context from the prompt, the SQL, or anything the model produced.

Guarantees (goals)​

For any SQL string, policy, and context, if HaltSQL returns allowed: true:

  1. The input is exactly one statement of an allowed kind.
  2. Every relation read or written is listed in the policy, and no system catalog is reachable.
  3. Every column referenced (including through * and whole-row references) is allowed.
  4. Every function, operator, and cast is allowed.
  5. Every occurrence of a tenant-scoped relation is filtered to the caller's tenant in its own scope (see tenancy.md).
  6. No construct with hidden side effects is present (data-modifying CTEs, SELECT ... INTO, locking clauses, EXPLAIN ANALYZE, disallowed functions).
  7. Size, depth, node, join, and LIMIT budgets are respected.

And in all cases:

  1. Fail closed. Parse errors, unsupported syntax, limit breaches, and internal errors produce allowed: false. verify never raises.
  2. Deterministic. The same inputs give the same verdict.

These are design goals backed by tests (see testing.md). HaltSQL 0.0.1 has not had an external security audit.

Known limitations and non-goals​

  • Not a replacement for database permissions or RLS. A bug in HaltSQL, a misconfigured policy, or a caller that skips the check would expose data if HaltSQL were the only control. See defense-in-depth.md.
  • No prompt-injection detection. HaltSQL judges the SQL, not the prompt.
  • Views and functions are opaque. If a policy allows a view or a function that reads other tenants' data internally, HaltSQL cannot see that.
  • Allowed data can still be misused. HaltSQL limits which rows and columns an agent can read. It does not decide whether showing allowed data to the user is appropriate.
  • Inference and timing channels. Aggregates over the caller's own tenant are allowed by design. HaltSQL does not prevent side-channel inference through query timing or error behavior on the database side.
  • Costly but allowed queries. A query within all limits can still be expensive (for example a large sort over the tenant's rows). Use statement_timeout and connection limits.
  • Grammar version. HaltSQL parses with the Postgres 17 grammar. Running against an older server is expected to work for the SQL HaltSQL allows, but is checked in the lab rather than guaranteed.
  • PostgreSQL only. Other dialects are out of scope before 1.0.

Trust boundaries in deployment​

  • Library: runs in your process; trust is the same as your application.
  • Sidecar: treat the network between the agent and haltsql-server as untrusted. Keep the listener on localhost in the same pod, or turn on the server's built-in TLS or mutual TLS (server.tls, see authentication.md), or terminate TLS in a proxy or service mesh in front of it. Use bearer tokens pinned to policies, and do not enable allow_unauthenticated outside development.
  • Audit logs may contain sensitive data if log_raw_sql is enabled. It is off by default.
