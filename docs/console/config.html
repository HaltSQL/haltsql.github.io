HaltSQL Console: configuration

haltsql-console --config console.yaml (or HALTSQL_CONSOLE_CONFIG). YAML or JSON. A complete example is deploy/console/console.example.yaml. Unknown keys are errors.

Secrets. Any string can contain ${env:NAME}, ${vault:...}, ${aws-sm:...} or ${gcp-sm:...}. Provider placeholders need a secrets: section with the same shape as the server's (secrets.md). $${ writes a literal ${. Resolved values are never logged or returned by the API.

When placeholders are resolved depends on the section:

  • At load: the sections the console reads at startup (listen, environment, state_dir, frontend_dir, auth, verifiers, fleet, audit, policies, data, agents). A placeholder that cannot be resolved is a startup error.
  • On demand: opa, integrations, signals and catalogs (catalogs are resolved on every catalog load, so a rotated catalog token is used by the next load; signals takes only numbers, so it has no placeholders in practice). At load each placeholder is only checked: valid syntax, a known scheme, the provider configured in secrets:, and for ${env:...} the variable set. Errors stop startup. The value is fetched only when a feature needs it (for example when it posts to Slack). Provider values are cached for at most 5 minutes, so a rotated secret is picked up without a restart, and the console does not keep these secrets in memory between uses.

The configuration document the console keeps for feature-specific keys is the file as written, with its placeholders unresolved.

auth​

At least one of oidc, proxy, tokens, dev. dev cannot be combined with the others.

KeyMeaning
oidc[]name, issuer, audience (or audiences), optional jwks_uri, groups_claim (default groups), group_prefix (default <name>:), leeway_seconds, allow_insecure_http (tests only). Tokens are verified like the server verifies callers (JWKS, iss, aud, expiry; RS256, ES256, PS256, EdDSA), and the sign-in must be recent enough for session_hours.
proxyTrusts identity headers set by an identity-aware proxy. See auth.proxy.
tokens[]name, sha256 (hex SHA-256 of the token), role. For automation.
devtrue, or { user, role }. The role defaults to dev. Every request without credentials is that user. Development only: see Dev mode. --dev ROLE does the same.
roles{ admin: [groups], owner: [...], analyst: [...], audit: [...], dev: [...] }. A user gets every role one of their groups maps to, and their permissions are the union of those roles. The most privileged role (admin, then owner, audit, analyst, dev) is shown as their primary role. A user whose groups map to no role is refused.
session_hours1 to 720, default 8. An OIDC token is refused with session expired; sign in again when its auth_time claim (or iat when there is no auth_time) is more than session_hours old. A token with neither claim is accepted until it expires, unless require_auth_time is set. Not applied to proxy headers or service tokens: set the session length on the proxy.
require_auth_timeDefault false. When true, an OIDC token without an auth_time claim is refused (session expired; sign in again), so session_hours is measured from the actual sign-in. Check that your provider sets auth_time (some only do when the client asks for it, for example with max_age). The Access page shows the Sessions safeguard as verified only when OIDC is the only auth method and this is true.

auth.proxy​

KeyMeaning
user_headerRequired. Header with the user's id (for example X-Auth-Request-Email).
name_headerOptional display-name header.
groups_headerOptional header with comma-separated groups.
group_prefixPrepended to each proxy group before role mapping. Default "". Set it (for example proxy:) when OIDC is also configured, so a proxy group can't collide with an OIDC group.

You must set trusted_proxies, the shared secret, or both. When both are set, both checks must pass. A request that carries user_header but fails a check gets 401 (proxy identity headers from an untrusted source). It is not treated as anonymous. Still make sure the console can only be reached through the proxy, and that the proxy strips these headers from client requests.

Dev mode​

auth.dev is refused at startup unless:

  • it is the only auth method: no oidc, proxy or tokens, and
  • listen is a loopback address: 127.0.0.0/8, ::1 ([::1]:port) or localhost. An empty host or * means 0.0.0.0, which is not loopback.

These rules also apply after --listen and --dev overrides (either one alone or both), and the server checks them again before it binds. When dev mode is not configured, a request without credentials is always 401.

In dev mode, every /api/ request must also be addressed to a loopback host: its Host header must be localhost, an address in 127.0.0.0/8 or [::1] (any port), else 403 HOST_NOT_ALLOWED. This blocks DNS rebinding, where a web page on another site resolves its own name to 127.0.0.1 and calls the console from the browser.

Origins​

State-changing /api/ requests (anything but GET, HEAD, OPTIONS) are checked against cross-site request forgery. A request without an Origin header (curl, scripts) passes. A request with one passes when:

  • public_url or allowed_origins is set: the Origin's scheme, host and port are one of the configured origins (a missing port is the scheme's default). The Host header is not used, so this works behind a reverse proxy or load balancer that rewrites Host.
  • neither is set: the Origin names the same host and port as the Host header. A proxy in front must then pass Host through unchanged.

Sec-Fetch-Site: cross-site is refused in both cases.

What each verifier kind exposes:

  • server: everything. /v1/admin/status needs server.admin enabled with the console's token in server.admin.callers; without it (404) the state comes from /readyz and /metrics only. A 401/403 is shown as the verifier's error.
  • mcp: polled the same way; a 404 on any endpoint is not an error.
  • proxy: haltsql-proxy has no HTTP endpoints. Give its PostgreSQL address as url (postgres://host:6432 or tcp://host:6432) and the console checks that it accepts TCP connections. An http(s):// url is polled like a server.

The admin token is sent to metrics_url only when it has the same scheme, host and port as url.

Rates (verifies_per_second), OPA decision counts, OPA errors (timeouts) and buffered-record peaks are computed from the last history_size polls kept in memory, so they restart from zero when the console restarts. Each sample is timestamped when that verifier's /metrics answer arrives, so a slow verifier does not skew the rates of the others.

Bundle source ids and last_error texts from the verifiers' admin status are shown to every role, so the console strips the query, fragment and userinfo from any URL in them (https://bucket/b.tar.gz?<redacted>) before they enter the fleet document.

RBAC for restarts​

A restart is the patch kubectl rollout restart sends (a new kubectl.kubernetes.io/restartedAt pod-template annotation) on the verifier's workload (deployment/<name> or statefulset/<name>). The console's service account needs only patch on those workloads in that namespace:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: haltsql-console-restart, namespace: haltsql }
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets"]
    # optionally pin resourceNames: ["haltsql-1", "haltsql-2"]
    verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: haltsql-console-restart, namespace: haltsql }
roleRef: { apiGroup: rbac.authorization.k8s.io, kind: Role, name: haltsql-console-restart }
subjects:
  - { kind: ServiceAccount, name: haltsql-console, namespace: haltsql }

Restarts need the restart_verifiers permission (admin) and a reason. The intent is written to the activity log as fleet.restart_requested (result: pending) before the Kubernetes call, and the restart is refused if that write fails; the outcome is then written as fleet.restart (ok, no_rollout or error, also when the Kubernetes call fails).

audit​

Where the console reads audit records. The console only reads; the verifiers keep writing their sinks as configured.

audit:
  sources:
    # one of these per location; a file is read by the first source that names it
    - { verifier: haltsql-1, file: /var/log/haltsql-1/audit.jsonl }
    - { verifier: auto, file: /var/log/haltsql/ }            # every *.jsonl / *.log inside
    - { verifier: auto, file: "/var/log/haltsql-proxy/audit-*.jsonl" }
    - { verifier: auto, s3: "s3://acme-audit/haltsql/", region: us-east-1 }
    - { verifier: auto, gcs: "gs://acme-audit/haltsql/" }
  retention_hours: 168
  max_records: 2000000
  poll_seconds: 5
KeyDefaultMeaning
sources[]noneExactly one of file (alias path), s3 or gcs, plus verifier. The same file, directory, glob or URI listed twice is a configuration error. A file matched by two sources (a file and the directory holding it) is read only by the first, and the later source reports it under overlaps in the ingest status.
sources[].verifierautoVerifier name the records belong to (matches verifiers[].name). With auto, the name comes from the object name (object sinks write <host>-<run>-<seq>-<sha256>.jsonl, so the host), else the file's basename without extension.
sources[].fileA file, a directory (every *.jsonl and *.log directly inside, in name order) or a glob with */? in the last path segment. Files are tracked by inode and tailed by byte offset through a descriptor kept open between polls; only complete lines are read. After a rename rotation the old file's unread tail is read first (record locations keep the path the file was first seen at), and a glob that also matches rotated names does not read a file twice. A file that shrinks, or whose first line changed (copytruncate), is read again from the start and the chain check reports a gap there instead of a break. A record identical to one already read for the same verifier is skipped.
sources[].s3s3://bucket/prefix. Every .jsonl object under the prefix is read once, in key order. Only keys from the YYYY/MM/DD/HH/ partition of the retention start on are listed (the object-sink layout; with a prefix that does not end in / the whole prefix is listed), and keys before it are forgotten. An object that cannot be read holds back the later objects of the same host and is retried on the next polls; after object_attempts failures it is skipped, listed under skipped_objects in the ingest status, and the chain check reports a gap. Credentials: AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY (optional AWS_SESSION_TOKEN), web identity (IRSA), ECS/EKS Pod Identity or the instance profile. Needs s3:ListBucket and s3:GetObject only.
sources[].regionAWS_REGION, else us-east-1S3 signing region.
sources[].endpointAWSS3-compatible endpoint (path-style; https, or http on loopback).
sources[].gcsgs://bucket/prefix, read like S3 through the JSON API. Credentials: GOOGLE_APPLICATION_CREDENTIALS (service-account key file), else the metadata server (Workload Identity). Needs storage.objects.list and storage.objects.get. STORAGE_EMULATOR_HOST overrides the API base: it must be https, or http on a loopback host, and no credentials are sent to it. Credentials are not cached after a failure, and a changed key file is re-read.
retention_hours168Records older than this are dropped from the in-memory index.
max_records2000000Index size cap; the oldest records are evicted first.
poll_seconds5How often every source is polled. A source that fails is retried after poll_seconds, doubled per consecutive failure up to 5 minutes.
max_object_mb256Largest S3/GCS object read; a larger one fails (and is skipped after object_attempts).
max_line_mb64A file line longer than this is skipped (it still counts for line numbers).
request_timeout_seconds60Timeout of each S3/GCS request.
relist_minutes10How often objects are listed from the retention start; in between, listings start at the partition of an hour ago. Objects uploaded late under an older partition (a spool replay) are picked up by the next full listing.
object_attempts5Failed reads before an object is skipped.
chain_check_seconds300How often the published audit-chain status is refreshed (incrementally).

Each verifier's records are numbered (seq) in the order they are read; the chain of custody check walks that order. Per-source state (records read, last successful read, last error, skipped_objects, overlaps, and next_poll while backing off) is kept as the console's ingest status for the other views. File I/O runs off the event loop, and object sources are polled concurrently (at most four at a time), so a slow mount or bucket does not hold up the others. Prefer a prefix that holds only HaltSQL audit objects.

policies and opa​

The console loads the same policies as the verifiers, for the Playground, policy detail, shadow reports and suggestions. Loading runs at startup and every 60 seconds; a load that fails anywhere keeps the last good set (like the server's hot reload), and the errors are shown in GET /api/v1/policies (errors, file basenames only). A policy file is read and parsed once per change: a reload reuses the parsed policy while the file's modification time and size are unchanged.

KeyMeaning
policies.server_configA haltsql-server config file. Only its policies section is decoded, with the server's loader: the console never resolves the server's other secrets (database, admin tokens, OPA headers), so its identity needs no access to them. A secret provider placeholder inside policies (for example a bundle key) is resolved through the file's own secrets: section, with one resolver kept for an hour across reloads. Supported: policies[].path, policies[].inline, and local signed bundles (policies[].bundle with public_keys and name_prefix; the signature is verified). Not fetched: remote bundle_source entries; their policies appear only through fleet status (loaded: false).
policies.filesPolicy files, or directories whose *.yaml/*.yml/*.json documents with kind: Policy are loaded (other documents, such as test suites, are skipped). They replace server-config policies of the same name, like the server's --policy flags.

Relative paths are resolved against the console config file's directory. A policy's version is the same sha256: the verifiers log as policy_version. A shadow sibling of policy P is a loaded shadow-mode policy named P-*, P_* or P.*; it is the default compare of GET /api/v1/policies/P/report and an agent's default shadow policy.

opa has exactly the shape of the server's opa block (url, decision_path, timeout_ms, on_error, headers, tls.ca_file). When set, the Playground asks OPA after a HaltSQL allow, with the same input document as the server (caller.type is playground), honouring timeout_ms and on_error.

policies:
  server_config: /etc/haltsql/server.yaml
  files: [/etc/haltsql/policies/drafts]
opa:
  url: https://opa.internal:8181
  decision_path: haltsql/allow
  timeout_ms: 500
  on_error: deny

signals​

Detectors run every 30 seconds (interval_seconds) over the record index, the fleet snapshot and the last audit-chain verification. Every key is optional; numbers may be integers or decimals unless the table says integer. Unknown keys, non-numbers and values outside the range are configuration errors at startup.

  deny_spike:   { window_minutes: 15, factor: 3.0, min_records: 50, min_baseline_rate: 0.01 }
  opa_errors:   { window_minutes: 15, min_records: 10 }
  shadow_ready: { min_records: 1 }
  new_caller:   { hours: 24 }
  interval_seconds: 30
  resolve_after_minutes: 30
  forget_after_days: 7
  max_reverify: 500
  notify_timeout_seconds: 5

sink_buffering, restart_pending and bundle_drift come from the fleet snapshot and chain_broken from the last chain verification; they have no settings. Detector output is kept in memory and rebuilt after a restart. Each pass yields to the HTTP server between detectors, groups records by caller once, and scans the whole index for first-seen callers only on the first pass, hourly, or when older records appear.

catalogs and data​

Catalogs are read at startup, every 15 minutes, and on POST /api/v1/data/refresh. Export files are parsed in a worker thread, so a large manifest.json never stalls the console, and the 15-minute reload re-parses a file only when its modification time or size changed; POST /api/v1/data/refresh always re-reads every file. A catalog that cannot be read is reported (in GET /api/v1/data/columns sources[].error and as error under Integrations); the others still load.

catalogs:
  - { kind: dbt, manifest: /etc/haltsql/catalogs/manifest.json }
  - { kind: unity, file: /etc/haltsql/catalogs/unity-column-tags.json }
  - { kind: datahub, file: /etc/haltsql/catalogs/datahub-export.json }
  # live fetch: see the note below; no live provider is built in yet
  # - { kind: openmetadata, url: https://om.acme.internal/api, token: "${vault:secret/om#token}", service: prod_pg, database: app }
  - { kind: file, file: /etc/haltsql/policies/pii.json, label: reviewed }
data:
  exceptions:
    - { column: app.customers.email, policy: support-copilot, owner: Lee Park, ticket: SEC-88, expires: "2027-02-01" }

The importers are the ones haltsql schema import and haltsql report --pii use (see schema-and-pii.md). Columns are merged per schema.table.column (lower-cased): tags and sources are the union.

Live fetches are non-authoritative. A catalog's view of table structure can lag behind the database, so a live-fetched source is reported with authoritative: false and only flags columns. The console never loads it as a policy catalog.

Status of a tagged column. allowed_by lists the loaded policies whose allowlist lets a SELECT read the column (the table is listed and the column is listed, or the table allows "*"). With no such policy the column is blocked. Otherwise it is exception when every allowing policy is covered by an unexpired data.exceptions entry for the column (an entry without policy covers every policy), and needs_review otherwise, including when the matching exception has expired. shadow_denials counts shadow-denied records that read the column (from the record, or re-derived from raw SQL when it was logged). The counts come from a background scan of the record index that runs every minute (and on POST /api/v1/data/refresh), so a new record is counted within about a minute; shadow_denials_counted in the document is when the last scan finished. Columns re-derived from SQL are cached per verifier and request id, dropped when the record leaves the index, and re-derived after a policy reload. The classification follows a policy reload immediately.

tests_pathtestsDirectory of test suites; tests are appended to <tests_path>/<policy>.yaml (created, pointing at the policy file, when absent).
branch_prefixhaltsql-console/PR branch is <branch_prefix><policy>; an open PR for the policy (the one the console stored, else any open PR GitHub has for that branch) is updated instead of opening another. A leftover branch with no open PR is reset to base only when its head is a commit the console made; otherwise the request is 409.
required_approvals1Shown next to the approvals in the PR state.
apihttps://api.github.comAPI base URL (GitHub Enterprise: https://ghe.example.com/api/v3). https, or http for loopback only.

Reads (GETs) are retried up to three times on a network error, a 5xx, a 429 or a rate-limit 403, honouring Retry-After and x-ratelimit-reset (a wait over 5 seconds is not taken: the call fails instead). Writes are never retried. Reviews and check runs are read 100 per page, following Link: rel="next" for up to 10 pages.

integrations.slack, integrations.pagerduty​

integrations:
  slack: { webhook: "${vault:secret/slack#webhook}" }
  pagerduty: { routing_key: "${vault:secret/pagerduty#key}" }
KeyMeaning
slack.webhookSlack incoming-webhook URL.
pagerduty.routing_keyPagerDuty Events API v2 integration (routing) key.
pagerduty.events_urlDefault https://events.pagerduty.com/v2/enqueue; override for a proxy or EU endpoint.

Each new high signal is posted to every configured channel (PagerDuty: event_action: trigger, dedup_key = the signal id, severity critical). When a high signal resolves (automatically, or a person sets resolved), the PagerDuty incident is resolved with event_action: resolve and the same dedup_key. Delivery is best effort: a request that gets HTTP 429, a 5xx or a transport error is retried twice (0.5 s, then 1 s later); other failures are logged with the HTTP status only, never the URL or key. Placeholders in these keys are resolved on each use; one that cannot be resolved is logged and the channel is skipped. Slack text escapes &, < and > in every field, so a caller name cannot mention @channel or disguise a link. URLs must be https (plain http only on a loopback host).
